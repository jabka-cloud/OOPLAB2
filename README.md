##  1. Цель работы
Реализовать систему, моделирующую игровую базу, ландшафт карты и нейтральные объекты, которые влияют на юнитов из предыдущей лабораторной работы (или их упрощённый аналог). Освоить паттерны проектирования: «Наблюдатель» (база следит за юнитами), «Прокси» (для взаимодействия с ландшафтом), «Стратегия» (разное влияние нейтральных объектов на типы юнитов). Реализовать перегрузку операторов (или их эквиваленты) для взаимодействия юнитов с нейтральными объектами.


##  2. Структура проекта и архитектура

Проект разделён на независимые логические модули:

| Модуль / Папка | Назначение | Ключевые классы и интерфейсы |
| :--- | :--- | :--- |
| **`Units`** | Иерархия бойцов, фабрика и пул характеристик | `Unit`, `Infantry`, `Archer`, `Mage`, `FlyingUnit`, `UnitFactory`, `UnitTypeInfo` |
| **`Base` и `Observer`** | Управление ресурсами базы и система событий | `Base`, `IObserver`, `IObservable`, `UnitEvent` |
| **`Terrain`** | Игровая сетка ландшафтов и кэширующий прокси | `Terrain`, `Plains`, `Forest`, `Swamp`, `Mountains`, `TerrainProxy`, `TerrainMap` |
| **`NeutralObject` и `Strategy`** | Объекты карты и алгоритмы их воздействия | `NeutralObject`, `Altar`, `Trap`, `TreasureChest`, `EnergySource`, `IInteractionStrategy` |
| **`Operators`** | Перегрузка операторов взаимодействия | `operator+`, `operator-`, `operator*`, `operator/` |
| **`Game`** | Контроллер симуляции и система логирования | `GameController`, `main.cpp` |

### Основные типы связей между классами
* **Наследование и реализация (Generalization / Realization):**
  * Конкретные юниты (`Infantry`, `Archer`, `Mage`, `FlyingUnit`) наследуются от абстрактного класса `Unit`, который реализует `IObservable`.
  * Класс `Base` реализует интерфейс `IObserver` для отслеживания состояния своих войск.
  * Типы ландшафта и обёртка `TerrainProxy` реализуют общий интерфейс `Terrain`.
  * Нейтральные объекты (`Altar`, `Trap`, `TreasureChest`, `EnergySource`) наследуются от `NeutralObject`.
* **Композиция (Composition):**
  * `GameController` единолично владеет картой `TerrainMap` через `std::unique_ptr`.
  * `TerrainMap` владеет двумерной матрицей клеток `std::unique_ptr<Terrain>`, а `TerrainProxy` оборачивает реальный ландшафт через `std::unique_ptr<Terrain>`.
* **Агрегация и Ассоциация (Aggregation / Association):**
  * `Base` хранит список активных юнитов в `std::vector<std::shared_ptr<Unit>>`.
  * `Unit` ссылается на неизменяемый объект параметров из статического пула `UnitTypeInfo` (`std::shared_ptr`) и хранит слабые ссылки на подписчиков (`std::weak_ptr<IObserver>`).
  * `NeutralObject` хранит словарь стратегий `std::map<UnitType, std::shared_ptr<IInteractionStrategy>>`.

##  4. Реализованные паттерны проектирования

| Паттерн | Класс(ы) в проекте | Решаемая задача и особенности реализации |
| :--- | :--- | :--- |
| **Flyweight** *(Приспособленец)* | `UnitTypeInfo` | Выносит общие неизменяемые характеристики юнитов в статический пул `pool` с ленивой инициализацией, исключая дублирование данных в памяти. |
| **Simple Factory** *(Простая фабрика)* | `UnitFactory` | Инкапсулирует создание конкретных подклассов юнитов по `UnitType`, разгружая класс `Base` (соблюдение SRP). |
| **Observer** *(Наблюдатель)* | `IObserver`, `IObservable`, `Base`, `Unit` | Обеспечивает автоматическое уведомление базы при ранении или гибели бойца. Использование `std::weak_ptr` предотвращает циклические ссылки. |
| **Proxy** *(Заместитель)* | `TerrainProxy` | Контролирует доступ к клеткам карты (`isOccupied`) и кэширует результаты проверки проходимости в `passabilityCache` для ускорения повторных запросов. |
| **Strategy** *(Стратегия)* | `IInteractionStrategy` и наследники | Позволяет нейтральным объектам (`Altar`, `Trap` и др.) динамически выбирать алгоритм воздействия в зависимости от типа подошедшего юнита. |
| **Facade** *(Фасад)* | `GameController` | Скрывает сложную координацию карты, базы, юнитов и логирования в `game_log.txt` за единым интерфейсом запуска сценариев `run()`. |

### Перегрузка операторов взаимодействия
Для интуитивного описания игровых действий реализованы бинарные операторы:
* `unit + chest` — открытие сундука с пополнением казны базы (`GoldRewardStrategy`).
* `unit - trap` — срабатывание ловушки с нанесением урона наземным юнитам (`DamageStrategy`).
* `unit * altar` — получение классового усиления от алтаря (`+атака`, `+дальность` или `+мана`).
* `unit / source` — восполнение запаса маны от источника энергии (`ManaRestoreStrategy`).

##  6. Выводы
В ходе выполнения работы спроектирована и реализована расширяемая архитектура тактической игры на C++17. Комбинация порождающих, структурных и поведенческих паттернов позволила разделить ответственность между модулями: добавление новых типов юнитов, ландшафтов или стратегий взаимодействия не требует изменения существующего кода контроллера и базы. Применение умных указателей `std::unique_ptr`, `std::shared_ptr` и `std::weak_ptr` полностью исключило утечки памяти и проблему висячих ссылок.
